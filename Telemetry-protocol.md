# Протокол телеметрии: узел ↔ портал

Договорённость между прошивкой WT32-ETH01 и порталом.
Меняется только по согласованию обеих сторон.

---

## Темы MQTT

```
weld/<node>/status      узел жив, раз в 30 секунд
weld/<node>/access      запрос допуска по карте
weld/<node>/access/ack  ответ портала (портал публикует, узел слушает)
weld/<node>/session     начало и конец сеанса сварки
weld/<node>/arc         начало и конец участка горения дуги
weld/<node>/samples     порции замеров
weld/<node>/live        живой поток для панели технолога
```

`<node>` — идентификатор платы, он же `node_id` у оборудования в портале.
Например `node-01`.

Портал подписывается на `weld/+/...` — плюс означает «любой узел».
Добавится второй аппарат, подписку менять не придётся.

---

## Общие правила

**Время.** Везде UTC в миллисекундах от начала эпохи (целое число).
Часы ESP32 после перезагрузки сбрасываются — узел обязан
синхронизироваться по NTP при старте, иначе метки бессмысленны.
Если синхронизации не было, узел ставит `"clock": "unsynced"`
в `status`, и портал помечает такие записи как сомнительные.

**Время берётся с узла, а не с момента получения.** При обрыве связи
порции копятся на плате и досылаются позже — время получения
к сварке отношения иметь не будет.

**Идентификатор сеанса** `sid` генерирует узел: `<node>-<время старта>`.
Так он уникален без обращения к порталу — узел должен уметь работать,
когда портал недоступен.

**Качество доставки.** `samples` и `session` публикуются с QoS 1 —
брокер подтверждает приём, при обрыве сообщение уйдёт повторно.
`live` и `status` с QoS 0 — потеря не страшна, зато не копятся.

## status — узел жив

Раз в 30 секунд. Нужен, чтобы на панели было видно, какие аппараты в сети.

```json
{
  "ts": 1790250000000,
  "node": "node-01",
  "uptime": 86400,
  "clock": "synced",
  "queued": 0,
  "arc": false
}
```

`queued` — сколько порций ждёт отправки на плате. Больше нуля значит,
что связь рвалась и узел досылает накопленное.

`arc` — горит ли дуга прямо сейчас.

## access — запрос допуска

Приложили карту. Узел спрашивает, можно ли варить.

```json
{
  "ts": 1790250001000,
  "node": "node-01",
  "uid": "0080a182",
  "req": "a7f3"
}
```

`uid` — номер карты в hex, нижним регистром. Печатный номер на карте —
тот же UID в десятичном виде с нулями до десяти знаков.

`req` — короткий случайный идентификатор запроса. Портал вернёт его
в ответе, чтобы узел понял, на что именно пришёл ответ.

**Ответ портала** в `weld/node-01/access/ack`:

```json
{
  "ts": 1790250001200,
  "req": "a7f3",
  "allowed": true,
  "welder": "Петров А. В.",
  "welder_id": 14,
  "methods": ["tig1", "tig2"],
  "reason": ""
}
```

При отказе `allowed: false` и `reason` с причиной: «карта не
зарегистрирована», «допуск просрочен», «нет допуска на этот способ».

**Если портал не ответил за 3 секунды** — узел действует по кэшу
последних успешных допусков. Если и кэша нет, сварка запрещена:
логика fail-closed, без авторизации аппарат не варит.

## session — сеанс сварки

Начало:

```json
{
  "ts": 1790250060000,
  "node": "node-01",
  "sid": "node-01-1790250060000",
  "event": "start",
  "uid": "0080a182",
  "mode": "по техпроцессу",
  "route_code": "1047382"
}
```

`mode` — один из трёх: `по техпроцессу`, `отработка`, `прихватка`.

`route_code` — что прочитано с QR маршрутного листа, как есть, строкой.
Формат задаёт MES и он может меняться, поэтому узел его не разбирает
и не проверяет длину. Если QR не сканировали, поле пустое,
и режим не может быть «по техпроцессу».

Конец:

```json
{
  "ts": 1790252400000,
  "node": "node-01",
  "sid": "node-01-1790250060000",
  "event": "stop",
  "arcs": 7,
  "arc_time_ms": 1284300
}
```

## arc — участок горения дуги

Дуга определяется по току, порог 5 А. Отдельного дискретного
сигнала нет.

```json
{
  "ts": 1790250075000,
  "node": "node-01",
  "sid": "node-01-1790250060000",
  "aid": 3,
  "event": "start"
}
```

`aid` — номер участка внутри сеанса, по порядку с единицы.

Конец участка приходит со сводкой за весь участок:

```json
{
  "ts": 1790250310000,
  "node": "node-01",
  "sid": "node-01-1790250060000",
  "aid": 3,
  "event": "stop",
  "duration_ms": 235000,
  "i_avg": 132.4,
  "i_min": 18.2,
  "i_max": 186.0,
  "u_avg": 11.8,
  "pulse_hz": 2.5
}
```

**Важно про импульсный режим.** Это три РАЗНЫЕ величины, и портал
сравнивает их с разными полями техкарты:

| поле | с чем сравнивается в карте |
|---|---|
| `i_avg` | диапазон `current_min` / `current_max` |
| `i_max` | `pulse_current` — ток импульса |
| `i_min` | `pause_current` — ток дежурной дуги |

Если сравнить максимум с диапазоном, каждый импульсный шов даст
ложное превышение, и системе перестанут верить на второй день.

## samples — порции замеров

Порция за 10 секунд: 100 окон по 100 мс. Шлётся по заполнении.
При обрыве связи копится на плате и досылается позже.

```json
{
  "node": "node-01",
  "sid": "node-01-1790250060000",
  "aid": 3,
  "seq": 12,
  "t0": 1790250180000,
  "dt": 100,
  "points": [
    [131.2, 18.0, 185.4, 11.7],
    [133.8, 18.4, 186.1, 11.9]
  ]
}
```

`seq` — номер порции внутри участка, по порядку. По нему портал
склеивает запись и видит пропуски.

`t0` — время первого окна. `dt` — шаг в миллисекундах.
Время каждого окна считается как `t0 + индекс * dt` — так сообщение
в несколько раз компактнее, чем с меткой у каждой точки.

`points` — массив из четырёх чисел на окно, в строгом порядке:

```
[ ток средний, ток минимум, ток максимум, напряжение среднее ]
```

Массивом, а не объектом с именами полей: за получасовой шов это
18 000 окон, и имена полей в каждом раздули бы трафик вчетверо.

## live — живой поток

Раз в секунду, одно усреднённое значение. Для панели технолога.
Не хранится, теряется без последствий.

```json
{
  "ts": 1790250181000,
  "node": "node-01",
  "sid": "node-01-1790250060000",
  "i": 132.4,
  "u": 11.8,
  "arc": true
}
```

## Что портал делает с этим

| пришло | куда легло |
|---|---|
| `session start` | новая `WeldingSession` в Postgres |
| `arc start/stop` | `ArcRun` со сводкой в Postgres |
| `samples` | точки в ClickHouse |
| `session stop` | закрытие сеанса, запуск разбора |
| `live` | в память, отдаётся на панель, не хранится |

Разбор после закрытия сеанса: определение проходов по накопленному
времени дуги, остановки, отклонения от режима, расчётный расход.
