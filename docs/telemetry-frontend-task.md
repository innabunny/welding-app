# Задание: раздел телеметрии на фронте, первый этап

## Что делаем

Два экрана в существующем портале:

1. **Оборудование в работе** — список постов: кто варит сейчас, кто стоит,
   с кем нет связи, у кого режим вне допуска
2. **Экран одного аппарата** — живые показания, график сеанса, участки
   дуги, отклонения

Сводку производства с Кз, расходом материалов и выпуском **не делаем**:
данных за период ещё нет, она покажет нули. Это следующий этап.

## Прежде чем писать код

Прочитай в проекте и следуй сложившемуся стилю, а не придумывай свой:

- `frontend/src/shared/api/client.ts` — как устроены запросы
- `frontend/src/features/equipment/queries.ts` — как оформлены хуки

- `frontend/src/shared/ui/` — готовые компоненты: `Card`, `Badge`,
  `Table`, `Button`, `Select`, `States`. Свои кнопки и таблицы
  не писать
- `frontend/src/app/router.tsx` и `frontend/src/layouts/navigation.ts` —
  куда вписать раздел
- `frontend/src/shared/lib/theme.ts`, `format.ts`, `cn.ts`

Новый код: `frontend/src/features/telemetry/`, страницы
в `frontend/src/pages/`.

Типы уже написаны и лежат в `frontend/src/shared/types/`:
`telemetry.ts`, `nodes.ts`, `shifts.ts`, `utilization.ts`,
`deviations.ts`. Поля в них соответствуют API — не переименовывать.

## Есть референс оформления

В docs/telemetry-demo.html лежит собранный прототип от заказчика. Код внутри минифицирован, читать его не надо — открой файл в Playwright и сними скриншоты, чтобы увидеть компоновку. Берём из него расположение блоков и смысл, вёрстку пишем свою под shared/ui.

**Что брать почти как есть** (адаптировав под `shared/ui` и реальные
типы): `src/components/PostScreen.tsx`, `SessionChart.tsx`,
`ArcTable.tsx`, `DeviationList.tsx`, `Badges.tsx`, `ModeChip.tsx`,
`src/components/dash/ActiveList.tsx`, `ActivePage.tsx`,
`src/lib/format.ts`, `chart.ts`, `colors.ts`, `useLive.ts`.

**Что не брать:** `src/lib/dashboard.ts` и `insights.ts` — там расчёты
на фронте, у нас они на бэкенде. `src/mock.ts` — заменяется запросами.
`src/node/` — прямой опрос узла по HTTP, порталу не нужен.

**Расхождения прототипа с нашим API:**

- в прототипе `Equipment.id` — строка и равна `node`. У нас `id`
  числовой, а `node_id` отдельное поле и может отсутствовать
- `Workshop.id`, `Welder.id` — у нас числа
- число смен в прототипе лежит в оборудовании; у нас — в графике цеха
- `WorkRecord.busyMs` / `processMs` → у нас `standbySeconds` /
  `arcSeconds` в `/api/utilization/`
- в прототипе тёмная тема. Портал светлый с переключателем: берём
  тему портала. Исключение — экран одного аппарата: его смотрят
  у станка с расстояния, там тёмный вариант с крупными цифрами
  оправдан, сделать отдельным режимом только для этого экрана

## API

Все адреса под `/api/`, авторизация по токену — как в остальном портале.
Ответы в camelCase (`djangorestframework-camel-case`).

### Список постов

```
GET /api/nodes/                     состояние узлов
GET /api/nodes/summary/             счётчики: online, offline, catchingUp
GET /api/welding-sessions/?active=1 сеансы, которые идут сейчас
GET /api/equipment/                 справочник оборудования
```

`NodeState.isOnline` — на связи ли узел. `silentSeconds` — сколько
секунд назад было последнее сообщение. `queued` больше нуля означает,
что узел догоняет накопленные данные.

### Экран аппарата

```
GET  /api/welding-sessions/<id>/            сеанс
GET  /api/welding-sessions/<id>/arcs/       участки дуги
GET  /api/welding-sessions/<id>/samples/    график всего сеанса
GET  /api/arcs/<id>/samples/?points=1200    график одного участка
GET  /api/deviations/?session=<id>          отклонения
POST /api/weld-decisions/                   решение по отклонениям
WS   /ws/telemetry/<node>/                  живые значения
WS   /ws/telemetry/                         все аппараты сразу
```

**График.** `samples` возвращает прореженные корзины: `i` — среднее,
`iMin` и `iMax` — границы разброса внутри корзины. Рисовать линией
среднего и полосой разброса вокруг (area между iMin и iMax). Выброс
виден всегда, потому что попадает в границы своей корзины. В ответе
есть `total` — сколько замеров было до прореживания; показать
«18 420 замеров, показано 2 000». `stepMs` — ширина корзины.

Разрывы в данных между проходами должны оставаться разрывами, а не
соединяться прямой линией. У recharts для этого `connectNulls={false}`.

**WebSocket.** Сообщения двух видов. `LiveTick` — текущие ток,
напряжение, горит ли дуга, раз в секунду. `TelemetryEvent` —
`session_start` и `session_stop`: по ним панель перерисовывается
без перезагрузки страницы.

Соединение закрывается с кодом **4001**, если пользователь не вошёл.
Это не обрыв сети: показать «войдите заново», а не «переподключаюсь».
При обычном обрыве — переподключение с нарастающей задержкой.

**Решение по отклонению.** `POST /api/weld-decisions/` принимает
`session` (обязательно), `weld` и `run` (могут быть пустыми),
`result`, `deviations` (список идентификаторов), `reason`,
`assignedControl`. Автора ставит сервер.

Для отклонений режима доступны «допущено», «на контроль»,
«на переварку»; для нарушений порядка — только «разобрано». Константы
`REGIME_RESULTS` и `ORDER_RESULTS` уже есть в `deviations.ts`.
При «на контроль» поле `assignedControl` обязательно, иначе сервер
вернёт 400.

Одно решение обычно закрывает несколько отклонений сразу: технолог
смотрит на шов, а не на каждую просадку. Предусмотреть выбор нескольких.

### Смена

```
GET /api/shift-schedules/current/?workshop=<id>
```

`inShift`, `onBreak`, `fundSeconds`, `elapsedSeconds`,
`remainingSeconds`, `progress`. Если `hasSchedule` равно false —
графика на цех нет, так и написать, а не показывать нули.

Когда смена не идёт (ночь, выходной, обед), писать это словами.
Не считать Кз от нуля.

## Чего в данных пока нет

Узел ещё не отправляет данные на портал — модуль отправки в прошивке
не написан. Поэтому на реальном узле проверить нельзя.

Для проверки данные подделываются через MQTT:

```bash
mosquitto_pub -h localhost -t weld/node-01/live \
  -m '{"node":"node-01","sid":"test-1","ts":1760000000000,"i":142.5,"u":12.3,"arc":true}'
```

Темы и формат — в `Telemetry-protocol.md` в корне проекта.

Учти при вёрстке: у многих полей значения будут пустыми. Экран должен
осмысленно выглядеть, когда нет сеанса, нет отклонений, нет связи
с узлом — это обычное состояние, а не ошибка. Пустые состояния брать
из `shared/ui/States.tsx`.

## Порядок работы

Делай по частям и показывай результат, а не всё сразу:

1. Хуки запросов и подключение WebSocket, без вёрстки — проверить,
   что данные доходят
2. Список постов
3. Экран аппарата: показания и график
4. Участки дуги и отклонения
5. Форма решения по отклонению

После каждой части — `npm run build` (там `tsc --noEmit` в скрипте),
типы строгие, `any` не использовать.
